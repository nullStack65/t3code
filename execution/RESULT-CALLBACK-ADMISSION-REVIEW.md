## Follow-up: projected provider identity may legitimately be absent

This follow-up checks whether the four failing fixtures alone explain the unknown-instance guard. They do not. The fixtures are incomplete at the provider-event boundary, but an absent identity in a retained thread projection is itself a supported legacy shape.

- OrchestrationSession declares providerInstanceId optional at [orchestration.ts:623](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/packages/contracts/src/orchestration.ts:623).
- Migration 028 adds nullable projection_thread_sessions.provider_instance_id without backfilling existing rows ([028_ProjectionThreadSessionInstanceId.ts:7](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/persistence/Migrations/028_ProjectionThreadSessionInstanceId.ts:7)). Migration 027 says the legacy provider runtime rows cannot be mapped to an account safely from driver alone ([027_ProviderSessionRuntimeInstanceId.ts:12](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/persistence/Migrations/027_ProviderSessionRuntimeInstanceId.ts:12)).
- The projector stores a missing event instance as SQL NULL ([ProjectionPipeline.ts:1350](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/orchestration/Layers/ProjectionPipeline.ts:1350)); snapshot mapping omits null from the returned session ([ProjectionSnapshotQuery.ts:379](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts:379)).
- Production provider events normally carry stronger identity: ProviderService correlates each event with its emitting registered instance ([ProviderService.ts:469](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/provider/Layers/ProviderService.ts:469)). ProviderRuntimeIngestion conditionally carries that ID into session-set events ([ProviderRuntimeIngestion.ts:1916](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts:1916)). The failing ingestion tests use a direct fake event source and omit this field, so those event fixtures should model the production boundary.
- More importantly, startup already calls ProviderService.listSessions for live sessions ([serverRuntimeStartup.ts:503](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/serverRuntimeStartup.ts:503)); ProviderService tags every result with its actual registered adapter instance ([ProviderService.ts:2124](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/provider/Layers/ProviderService.ts:2124)). Startup currently retains only the thread IDs from that enumeration. Active projected sessions are excluded from orphan reconciliation without refreshing their projected route ([serverRuntimeStartup.ts:536](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/serverRuntimeStartup.ts:536)); commands become ready only after reconciliation ([serverRuntimeStartup.ts:1066](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/serverRuntimeStartup.ts:1066)). Therefore an upgraded server can accept commands while a live retained session has no projected instance ID even though the provider service knows its exact instance.
- ProviderService has no per-thread active-session lookup; listSessions enumerates live sessions from all registered adapters. ProviderSessionDirectory.getBinding(threadId) is targeted, but legacy null rows are promoted to the driver's default instance ([ProviderSessionDirectory.ts:60](/Users/businessaccount/.local/share/delivery-workspaces/t3-callback-admission-review-20261002/apps/server/src/provider/Layers/ProviderSessionDirectory.ts:60)), while migration 027 documents that this historical mapping can be ambiguous. That default must not be treated as authoritative account identity for a live old session.

Do not accept a test-only fixture-binding repair as complete. Correct fake event fixtures to include the emitting provider instance and intended driver, but retain a regression for an active session with no projected providerInstanceId. Reconcile the projection from exact live-session identity before admission (the existing startup enumeration already gets that information before command readiness), preserving lifecycle fields and changing only the missing route. If the active instance cannot be resolved safely, retain fail-closed rejection before message, turn or lifecycle mutation. Do not infer account identity from providerName, thread model selection or legacy default promotion.

The regression should prove: a known compatible live instance permits supported continuation/model changes; a known incompatible instance rejects before mutation and preserves the session; and an unresolved instance still fails closed. Reuse the existing startup enumeration or another truly per-thread authoritative interface. Add no list-all polling per command or routing framework.
