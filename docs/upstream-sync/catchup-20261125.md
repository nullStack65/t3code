## Resolutions toward upstream

Where upstream and the fork changed the same thing, upstream's version stands except where
a fork behaviour is listed under "Fork behaviour kept".

1. Migration ids. Upstream's migrations 97 to 117 are registered at their upstream id plus
   `UPSTREAM_MIGRATION_ID_OFFSET` (6), so they run as 103 to 124 (118, WorkflowPools, is the newest). See the next section.
2. Unconfigured provider instances. The release treated every instance missing from the
   machine's settings as disabled for queued runs (#192); upstream treats it as enabled. With
   upstream's new rule that a message arriving before the latest run's checkpoint capture
   commits queues behind it, the release's rule held every such queued run forever; the
   queued-turn replay fixtures for ACP, Cursor, Fx, Kiro and Grok caught it. Upstream's rule
   stands for a built-in driver's default instance. The fork keeps one part: a custom
   instance the machine no longer configures is gone, so its queued runs stay held (the
   fork's removed-instance test).
3. A queued run on another provider instance reserves its own provider thread; it no longer
   borrows the active run's (upstream's edited-queued-run test requires it).
4. Antigravity. #158 (quota from the CLI sign-in) is superseded by upstream's implementation
   (`AntigravityProtocol.ts` is upstream's file; `antigravityUsageLimits.ts` is upstream's
   plus the fork's "Not applicable: API keys and Agent Platform are billed by Google" row).
   #162 (hold an Antigravity run while its command runs) is superseded by upstream's ACP
   adapter, which the fork's `AntigravityAdapterV2.test.ts` cases pass against unchanged.
5. Voice settings. Upstream's destination picker replaces the fork's separate "Transcription
   environment" row and backend picker (#84). Kept: Groq first in the menu order, the
   first-visit recommended backend, the Groq and AssemblyAI providers and the Groq stream path.
6. Delegation and sessions. Detaching a session (a workspace handoff) no longer notes its
   background work as lost, as upstream's test requires; closing it still does (#172).
7. Event subscriptions. Subscribing to a pull request that already merged or closed no longer
   errors with `PullRequestNotOpenError`: the subscription is stored and the ended state is
   reported, as upstream's watch tool does. This is a behaviour change from the release.
8. Usage notices. `collectLimitNotices` is upstream's relocated function; the fork's magpie
   billing-refusal notice and its "Not applicable:" suppression are ported onto it.
9. Provider failure details keep both the fork's `httpStatus` and upstream's
   `verificationUrl`; thread search keeps both the fork's sender filter and upstream's
   phrase search.
10. Delegated task and worker-alert wording. The fork's "Worker alert: it ran X instead of Y"
    text stands; upstream tests that quote the old wording were updated to it.
11. Duplicate declarations, dropped closing braces and unbalanced test blocks left by the hand
    resolution were repaired. Eight exports that make `knip` fail on the release tip itself
    were un-exported, which the pre-commit hook needs before any commit can pass.
12. The fork's delivery-class test harness waited for a finished run to reach `waiting`;
    upstream completes the run directly and keeps `waiting` for legacy runs, so four digest
    and `when_idle` tests timed out. The harness now waits for `completed`, as upstream's own
    helper does. Production code is unchanged by this.
13. The upstream lint config now enforces `t3code/no-untranslated-copy`, which the fork's
    own copy failed in about 190 places. It is wrapped for translation, the catalogs are
    regenerated, and `vp lint` is clean across the repository.

## Compatibility: migrations

Deployed fork databases record the fork's migrations at ledger ids 97 to 102 (founder
enrollment, corrections, the latest-visible-message index, event subscriptions and
scheduled-task occurrences), and upstream's own migrations 97 to 118 use the same numbers
for different work. Renumbering the fork's migrations would have made the migrator skip
upstream's schema on a fork database, so the fork's ids stay and upstream's move up.

- Fork databases at 97 through 102, and fresh installs, upgrade through every later id.
- A database a plain upstream build wrote (its names at 97 to 118) is refused by name, with
  the ledger untouched; it is never skipped past.
- The tests are in `Migrations.test.ts` ("the fork's migration ledger") and
  `reconcileV2PreviewMigration.test.ts`, which now derives its expected ledger from the manifest.
- The npm launcher's `databaseMigration` is read from the manifest (it was the highest file
  number, which is no longer the highest id).
- Standing cost: every future upstream migration N is registered as `N + UPSTREAM_MIGRATION_ID_OFFSET`
  when the sync merges it (migration 118 already was). `Migrations.test.ts` fails if a
  migration file is not registered or an id repeats.
