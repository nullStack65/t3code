# Watcher thread

One thread, by default Kameron's CoS on the laptop, hears model, usage-limit and link alerts from every linked environment. A `thread-failed` event starts a watcher turn for a failed, unsettled top-level thread with no recorded launcher, such as one a person created. Other thread events go to the thread that launched the lane, read from the lane's `inbox.origin`, else `inbox.requestedBy`. If the launcher is archived, deleted or unknown, those launcher events go only to `modelAlertWebhookUrl` when configured. The server decides each event from thread state with no agent judgment, queues it durably, and retries until the receiving machine answers.

| Event                  | Fires when                                                                                                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `model-degraded`       | A run ran another model than selected, hit a provider fallback, or hit a usage limit.                                                                                                                                          |
| `thread-failed`        | A top-level thread with no recorded launcher failed, other than at a usage limit. The server wakes the configured watcher.                                                                                                     |
| `lane-ended`           | A top-level lane's run ended `failed` or `interrupted`, or `completed` with open pull requests and nothing tracked to wake it.                                                                                                 |
| `promise-without-wake` | A lane went idle or settled after saying it will be woken or will continue later, with no background task, pull request watch, delegated task or armed resume. The phrase list is `PROMISE_PHRASES` in `ThreadEventAlerts.ts`. |
| `stuck`                | An active run has had no new activity for `watcherStuckMinutes` (default 20; 0 turns it off), or a thread waits on background work that no longer exists. A parent whose child threads are active is not stuck.                |
| `needs-person`         | An agent-created lane raises a pending question or approval, or its inbox is assigned to a founder or set to `action`.                                                                                                         |

A failure at a usage limit is reported only in that limit's one grouped alert, and a failure wake waits while the watcher itself is stopped at its usage limit. After a failure wake, another failure on that thread waits five minutes from delivery. The server checks that the failed run is still current before sending it. The receiving watcher decides whether to retry or escalate.

Each event reports once per thread and kind until its state changes: a new run, a different message, or the condition clearing. Delivery judges each event again, as of when it fired, and drops one that is no longer true: the lane restarted, settled, registered a wait, merged its pull request or got its answer. A dropped event stays reported, so the same state coming back does not alert again until its run or message changes. While the watcher is busy (running, queued or waiting), every alert to it, including model and usage-limit alerts, waits up to 10 minutes instead of queueing behind that turn, so it is judged when the watcher can act. A held alert is looked at again on a later flush, about every 30 to 60 seconds. Delegated children are skipped; their parent already hears their result. The watcher thread never reports about itself.

## Moving the watcher

The watcher is the `modelAlertWatcher` server setting (`{ environmentId, threadId }`, or `null` for none). Its Closura default is in `packages/contracts/src/settings.ts` (`DEFAULT_MODEL_ALERT_WATCHER`). To move the watcher, for example to an always-on machine such as the R720, change that one default and ship a build, or set `modelAlertWatcher` in each machine's settings to override it. `modelAlertWebhookUrl` additionally POSTs the existing digest alerts as JSON. Failure wakes go directly to the configured watcher.
