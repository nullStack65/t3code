# Closura thread inbox candidate

This additive candidate targets fork base `05993d81` (0.0.42, orchestration protocol 1), not upstream 0.1.9 or installed protocol 2 servers. Never install this older server against a newer host's existing userdata. It requires a separately tested port onto the fleet's qualified source version before deployment. It does not change AssemblyAI, host databases, linked-environment configuration, or CLO-802 wake delivery.

The `threadInbox` descriptor capability advertises typed classification and scoped inbox access. Clients must check this capability before offering classification mutations. Missing capability means ownership is unknown, not inferred from titles, machine, or project. The native client aggregation retains each environment/thread reference; no database is copied.

An existing access administrator can issue a pairing credential with `inboxIdentity` containing an actor (`human` with id `kameron` or `jeff`, or `agent` with a stable id), explicit `delegatesTo` founders, and `operational`. Pairing binds that identity into the destination's authenticated session subject. Never send identities as request labels or reuse an unrestricted host credential as a founder credential. Transport scopes still apply. Operational visibility is explicit; it does not grant host APIs to scoped identities.

Scoped identities can create coordinator inbox records, read authorized threads, update routing, and settle/unsettle them. Cross-founder routing requires an explicit delegation in the issued identity. Creation stamps requester, actor, and actual executor environment; reassignment cannot rewrite them. Unknown legacy threads remain unclassified and visible to operational identities. The home view shows actionable and FYI assignments and an authorized Operations view.

Scoped identities cannot start provider processes, change execution contexts, obtain file/terminal/attachment APIs, or mint other sessions. Attachment access currently fails closed, including authorized attachments; attachment delivery is not implemented for scoped identities. This is a deliberate capability limitation, not successful asset acceptance. Enabling provider execution requires a separately qualified isolation boundary: an agent with host file or shell access can read the event database and defeat thread privacy. Existing unrestricted host sessions and provider MCP credentials retain that authority. This candidate does not secure data against host administrators, existing signed asset URLs, or host-capable agents.

Before rollout, the source owner must finish real authenticated transport denial/stream tests, scoped attachment delivery, client identity-bound view selection and cache revocation, and a real-client UI pass. Mobile inbox UI and protocol 2 peer-link/OAuth propagation remain unimplemented. Root owns green-check review, merge and live deployment; this branch must not be presented as fleet-ready.

Recovery for an isolated synthetic evaluation is to stop only that evaluation's captured process and return to the prior source/config. No production downgrade or schema rollback is authorized. Do not restore or delete historical events, copy databases, or use backups as fixtures.
